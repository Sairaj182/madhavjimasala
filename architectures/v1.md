### Key Architectural Decisions

**Two separate Next.js deployments — not one monorepo app with `/admin` routes.**
The admin panel and user website have different audiences, different caching strategies, different auth requirements, and different deployment cadences. Coupling them creates headaches as the system grows.

**API layer inside Next.js route handlers (`/app/api/...`).**
No separate Express or FastAPI server. Vercel serverless handles this fine at current and projected scale. All admin-facing routes live under `/api/admin/` and are protected at the middleware level before any route handler executes.

**Cloudinary handles all image I/O.**
Images upload directly from the browser via a signed upload preset — they never touch your Vercel function. The CDN URL is stored in MongoDB. The user website fetches images directly from Cloudinary's CDN with on-the-fly transformations.

## 2. MongoDB Schema Design

### 2.1 Products Collection

```js
{
  _id: ObjectId,
  slug: String,           // "kashmiri-red-chilli-powder" — URL + lookup key
  name: { en: String, hi: String },   // bilingual for future expansion
  description: String,

  // Categorization
  categoryId: ObjectId,   // ref → categories
  tags: [String],         // ["chilli", "whole-spice", "premium"]

  // Pricing + Stock
  variants: [{            // 100g, 250g, 500g, 1kg
    sku: String,          // "MMK-CHI-250"
    weight: Number,       // grams
    unit: String,         // "g" | "kg" | "piece"
    price: Number,        // in paise (₹ × 100) — never store floats for money
    mrp: Number,
    stock: Number,
    lowStockThreshold: Number,
  }],

  // Images
  images: [{
    cloudinaryId: String, // "madhavji/products/kashmiri-chilli-01"
    url: String,          // full CDN URL
    alt: String,
    isPrimary: Boolean,
    order: Number,
  }],

  // Status
  isActive: Boolean,
  isFeatured: Boolean,

  // SEO
  seo: {
    metaTitle: String,
    metaDescription: String,
  },

  // Audit
  createdBy: ObjectId,    // ref → users
  createdAt: Date,
  updatedAt: Date,
}
```

**Indexing strategy:**

```js
// Compound index for public catalog (most common query)
{ isActive: 1, categoryId: 1, createdAt: -1 }

// Slug lookup for product detail pages (SSG/ISR)
{ slug: 1 }  // unique

// Featured products for homepage
{ isActive: 1, isFeatured: 1 }

// Atlas Search index on: name.en, description, tags
// Enables fuzzy full-text search without regex table scans
```

**Design reasoning:**
- Variants are embedded because they are always fetched and written together. A spice product will never exceed ~6 variants, so document bloat is not a concern.
- Images are embedded for the same reason — a product page always needs all images.
- Prices stored in paise (integer) to avoid floating-point precision errors in financial calculations.

### 2.2 Users / Staff Collection

```js
// Handles both admin accounts and staff employees in one collection
{
  _id: ObjectId,

  // Identity
  name: String,
  email: String,         // null for shop-floor staff without email
  phone: String,

  // Auth (only for admin/manager accounts)
  passwordHash: String,  // bcrypt
  refreshTokenHash: String,

  // Role
  role: String,          // "superadmin" | "admin" | "manager" | "staff"
  isActive: Boolean,

  // Staff-specific fields (null for admin-only accounts)
  staffDetails: {
    employeeId: String,  // "MM-0042"
    designation: String, // "Floor Manager"
    department: String,  // "Production" | "Packing" | "Sales"
    dateOfJoining: Date,
    dateOfLeaving: Date,

    salary: {
      type: String,      // "monthly" | "daily"
      amount: Number,    // monthly base in paise
      dailyRate: Number, // for daily wage workers
    },

    bankDetails: {
      accountNumber: String,  // encrypted at application layer
      ifsc: String,
      accountName: String,
    },

    documents: [{
      type: String,          // "aadhar" | "pan" | "photo"
      cloudinaryId: String,
    }],
  },

  createdAt: Date,
  updatedAt: Date,
}
```

**Design reasoning:**
Admin accounts and staff employees share 80% of their structure. Role-based access control handles what each type can do. Splitting into two collections creates cross-collection complexity with no benefit. `staffDetails` is embedded because staff details are always needed together when viewing an employee profile.

### 2.3 Attendance Collection

```js
// One document per employee per day
{
  _id: ObjectId,
  userId: ObjectId,       // ref → users
  date: Date,             // 2024-01-15T00:00:00Z — midnight UTC, normalized

  status: String,         // "present" | "absent" | "half-day" | "holiday" | "leave"

  // For present/half-day
  checkIn: Date,
  checkOut: Date,

  // For payroll calculation
  effectiveDays: Number,  // 1.0 | 0.5 | 0.0 — computed on save

  notes: String,
  markedBy: ObjectId,     // ref → users

  createdAt: Date,
  updatedAt: Date,
}
```

**Indexing strategy:**

```js
// Core query — all attendance for a month, for payroll
{ userId: 1, date: 1 }  // unique compound

// Monthly aggregation across all employees
{ date: 1, status: 1 }
```

**Design reasoning:**
One document per day makes inserts simple and makes it easy to re-mark a single day. One document per employee per month would make correcting a single day extremely complex (updating a nested array element).

### 2.4 Payroll Collection

```js
// One document per employee per month
{
  _id: ObjectId,
  userId: ObjectId,
  month: Number,          // 1–12
  year: Number,

  // Attendance summary (computed from attendance collection)
  workingDays: Number,
  presentDays: Number,    // includes 0.5 for half-days

  // Earnings
  basicSalary: Number,    // base amount in paise
  earnedSalary: Number,   // basicSalary × (presentDays / workingDays)
  bonus: Number,
  otherAllowances: Number,

  // Deductions
  deductions: [{
    reason: String,       // "late fine" | "advance recovery"
    amount: Number,
  }],

  // Computed totals
  grossSalary: Number,
  totalDeductions: Number,
  netSalary: Number,

  // Status
  status: String,         // "draft" | "approved" | "paid"
  paidAt: Date,
  approvedBy: ObjectId,

  notes: String,
  createdAt: Date,
  updatedAt: Date,
}
```

**Design reasoning:**
Deductions for a pay period are always read and written as a set. There will typically be 0–5 deductions per month per employee — embedding keeps payroll calculation to a single read. Unique index on `{ userId, month, year }` ensures idempotent payroll generation.

### 2.5 Inventory Collection

```js
// Main inventory document
{
  _id: ObjectId,
  itemType: String,       // "raw-material" | "finished-good" | "packaging"

  name: String,
  unit: String,           // "kg" | "piece" | "litre" | "bag"

  currentStock: Number,
  minStockLevel: Number,  // triggers low-stock alert
  maxStockLevel: Number,

  lastPurchasePrice: Number,  // in paise per unit
  averageCostPrice: Number,   // weighted average

  productId: ObjectId,    // ref → products (for finished goods only)

  // Last 50 movements embedded for quick display
  recentMovements: [{
    type: String,         // "in" | "out" | "adjustment"
    quantity: Number,
    reason: String,       // "purchase" | "production" | "damage"
    reference: String,    // PO number or order ID
    date: Date,
    recordedBy: ObjectId,
  }],

  createdAt: Date,
  updatedAt: Date,
}

// Full audit trail in a separate collection
// inventory_movements collection
{
  _id: ObjectId,
  inventoryItemId: ObjectId,
  type: String,
  quantity: Number,
  stockBefore: Number,
  stockAfter: Number,
  reason: String,
  reference: String,
  recordedBy: ObjectId,
  createdAt: Date,
}
```

**Design reasoning:**
The main inventory document embeds the last 50 movements for fast admin panel display. The full audit trail lives in a separate `inventory_movements` collection. This avoids paying the cost of fetching years of movements just to render the current stock level.

### 2.6 Orders Collection (Future-Ready)

```js
{
  _id: ObjectId,
  orderNumber: String,    // "MM-2024-00042" — human-readable

  customerId: ObjectId,
  customerSnapshot: {     // embedded at order time — survives future customer edits
    name: String,
    phone: String,
    email: String,
    address: {
      line1: String,
      city: String,
      state: String,
      pincode: String,
    },
  },

  // Snapshot pricing at time of order — non-negotiable
  items: [{
    productId: ObjectId,
    productName: String,  // snapshot
    sku: String,
    variantLabel: String, // "250g"
    quantity: Number,
    unitPrice: Number,    // price at time of order
    totalPrice: Number,
  }],

  subtotal: Number,
  discount: Number,
  deliveryCharge: Number,
  total: Number,

  // Status machine with full history
  status: String,         // "pending" | "confirmed" | "processing" | "shipped" | "delivered" | "cancelled"
  statusHistory: [{
    status: String,
    changedAt: Date,
    changedBy: ObjectId,
    note: String,
  }],

  // Payment (future)
  payment: {
    method: String,       // "cod" | "razorpay" | "upi"
    status: String,       // "pending" | "paid" | "refunded"
    transactionId: String,
    paidAt: Date,
  },

  createdAt: Date,
  updatedAt: Date,
}
```

**Critical design decision — snapshot pricing:** Product prices, names, and descriptions are copied into the order document at placement time. If you reference the live product and the admin later changes the price or deletes the product, every historical order becomes corrupted. The snapshot ensures order history is immutable.

### 3.10 Validation Strategy

Use `zod` schemas defined once and shared between client-side form validation and server-side API guards. Never trust client-sent data.

```js
// lib/validations/product.ts
import { z } from "zod";

export const createProductSchema = z.object({
  name: z.object({
    en: z.string().min(2).max(100),
    hi: z.string().optional(),
  }),
  slug: z.string().regex(/^[a-z0-9-]+$/).min(3).max(100),
  categoryId: z.string().length(24),  // ObjectId length
  variants: z.array(z.object({
    sku: z.string().min(3),
    weight: z.number().positive(),
    unit: z.enum(["g", "kg", "piece"]),
    price: z.number().int().positive(),  // paise
    mrp: z.number().int().positive(),
    stock: z.number().int().min(0),
    lowStockThreshold: z.number().int().min(0),
  })).min(1),
  isActive: z.boolean().default(true),
});

// Same schema used in route handler:
const body = createProductSchema.safeParse(await req.json());
if (!body.success) {
  return NextResponse.json({
    success: false,
    error: { code: "VALIDATION_ERROR", fields: body.error.flatten().fieldErrors }
  }, { status: 400 });
}
```

**HTTP status codes used consistently:**

| Code | Meaning |
|------|---------|
| `200` | Successful read or update |
| `201` | Successful create |
| `400` | Validation error (bad input) |
| `401` | Not authenticated |
| `403` | Authenticated but role check failed |
| `404` | Resource not found |
| `409` | Conflict (e.g. duplicate slug) |
| `500` | Server error — always log, never expose internals |

## 4. Data Flows

### Flow 1: Admin Creates a Product With Images

```
Admin fills form → selects images
  │
  ├─► Client requests signed Cloudinary upload URL
  │      POST /api/admin/cloudinary/sign-upload
  │
  ├─► Images upload directly browser → Cloudinary
  │      (Cloudinary returns cloudinaryId + URL for each image)
  │
  ├─► Admin submits form with image metadata + product data
  │      POST /api/admin/products
  │         → Zod validation
  │         → Check slug uniqueness
  │         → Insert to MongoDB
  │         → Return created product
  │
  └─► ISR revalidation triggered for user website
         next.js revalidatePath('/products')
         next.js revalidatePath('/products/[slug]')
```

> **Key pattern:** Images go browser → Cloudinary directly. Vercel functions have a 4.5MB body limit. Routing large uploads through your API function hits that limit on day one.

### Flow 2: User Browsing Products (The Hot Path)

```
User opens /products page
  │
  ├─► Next.js checks Vercel Edge Cache
  │
  ├─► Cache HIT → serve stale-while-revalidate response (< 5ms)
  │
  └─► Cache MISS → call /api/public/products
         → MongoDB query: { isActive: true, categoryId: ... }
            uses compound index { isActive:1, categoryId:1, createdAt:-1 }
         → Return 12 products with projected fields only
            (slug, name, primaryImage, variants.price, isActive)
         → Cache response for 60 seconds
         → Images served from Cloudinary CDN
            with transformation: ?f_auto,q_auto,w_400
```

### Flow 3: Monthly Payroll Generation

```
Admin clicks "Generate Payroll — January 2025"
  │
  └─► POST /api/admin/payroll/generate { month: 1, year: 2025 }
         │
         ├─► Query attendance collection:
         │      { userId: { $in: [...allStaffIds] },
         │        date: { $gte: Jan1, $lte: Jan31 } }
         │
         ├─► Aggregate effectiveDays per userId
         │
         ├─► For each staff member:
         │      earnedSalary = (basicSalary / workingDays) × effectiveDays
         │      netSalary = earnedSalary + bonus - totalDeductions
         │
         ├─► Upsert payroll documents (status: "draft")
         │      findOneAndUpdate with upsert: true
         │      unique index { userId, month, year } ensures idempotency
         │
         └─► Return summary for admin review
```

### Flow 4: Future Order Placement (E-Commerce Ready)

```
Customer checks out cart
  │
  └─► POST /api/public/orders
         │
         ├─► Validate cart items exist and are active
         │
         ├─► Start MongoDB transaction
         │      ├─► Verify stock for each variant
         │      ├─► Decrement stock on each variant
         │      ├─► Snapshot product prices and names
         │      ├─► Create order document
         │      └─► Clear cart document
         │
         ├─► Initiate Razorpay payment
         │
         └─► Razorpay webhook → POST /api/webhooks/razorpay
                → Verify signature
                → Mark order.payment.status = "paid"
                → Trigger fulfilment notifications
```

## 5. Scaling Strategy

### Current → Future Scale

| Dimension | Today (100 users/day) | Target (10k users/day) |
|-----------|----------------------|------------------------|
| MongoDB tier | M10 shared ($57/mo) | M30 dedicated ($210/mo) |
| Reads strategy | Direct DB queries | ISR + edge cache |
| Search | Atlas Search | Atlas Search (scales well) |
| Connections | Basic pooling | Connection pool tuned |
| Images | Cloudinary CDN | Cloudinary CDN (no change) |

### Vercel ISR — Primary Scaling Weapon

Product detail pages are pre-rendered at build time and regenerated every 5 minutes, or on-demand when the admin updates a product. At 10k users/day, a popular product page might receive 500 views/day. With ISR, those 500 requests hit the CDN edge, not MongoDB. The database sees 1 request (the regeneration), not 500.

```js
// app/products/[slug]/page.tsx
export const revalidate = 300; // 5 minutes

// On admin update, trigger immediate revalidation:
import { revalidatePath } from "next/cache";
revalidatePath('/products');
revalidatePath(`/products/${slug}`);
```

### MongoDB Connection Pooling

Vercel serverless functions are stateless. Without connection reuse, each invocation opens a new MongoDB connection — this kills Atlas at scale. Fix it with one pattern in your Mongoose connection file:

```js
// lib/mongodb.ts
import mongoose from "mongoose";

declare global {
  var mongoose: { conn: typeof import("mongoose") | null; promise: Promise<typeof import("mongoose")> | null };
}

let cached = global.mongoose ?? { conn: null, promise: null };
global.mongoose = cached;

export async function connectDB() {
  if (cached.conn) return cached.conn;

  if (!cached.promise) {
    cached.promise = mongoose.connect(process.env.MONGODB_URI!, {
      maxPoolSize: 10,
      serverSelectionTimeoutMS: 5000,
    });
  }

  cached.conn = await cached.promise;
  return cached.conn;
}
```

### API Response Caching

Public product endpoints return aggressive cache headers. At 10k users/day hitting `/api/public/products`, MongoDB may only see 1,440 actual queries (once per minute per cache TTL) instead of 10,000.

```js
return NextResponse.json(data, {
  headers: {
    "Cache-Control": "public, s-maxage=60, stale-while-revalidate=300",
  },
});
```

## 6. Security Design

### Authentication Flow

JWT with short-lived access tokens (15 minutes) and long-lived refresh tokens (7 days, stored as httpOnly cookie, hash stored in DB).

- Access token: in memory on the client — never `localStorage`
- Refresh token: httpOnly cookie — inaccessible to JavaScript
- On access token expiry: client silently requests a new one using the refresh cookie
- On logout: refresh token hash deleted from DB, invalidating the session server-side

### Role Hierarchy

```
superadmin  → all operations
admin       → all except delete superadmin accounts
manager     → read/write products, attendance, inventory; read-only payroll
staff       → mark own attendance only (optional self-service portal)
```

### Middleware Protection

```js
// middleware.ts — runs at the Vercel edge before any route handler
export function middleware(request: NextRequest) {
  if (request.nextUrl.pathname.startsWith('/api/admin')) {
    const authHeader = request.headers.get('authorization');
    const token = authHeader?.replace('Bearer ', '');

    if (!token) {
      return NextResponse.json({ success: false, error: { code: 'UNAUTHORIZED' } }, { status: 401 });
    }

    const payload = verifyJWT(token);
    if (!payload) {
      return NextResponse.json({ success: false, error: { code: 'INVALID_TOKEN' } }, { status: 401 });
    }

    // Pass identity to route handler via headers
    const requestHeaders = new Headers(request.headers);
    requestHeaders.set('x-user-id', payload.userId);
    requestHeaders.set('x-user-role', payload.role);

    return NextResponse.next({ request: { headers: requestHeaders } });
  }
}

export const config = {
  matcher: ['/api/admin/:path*'],
};
```

Route handlers then enforce role checks:

```js
// In any admin route handler
const role = request.headers.get('x-user-role');
const allowedRoles = ['admin', 'superadmin'];

if (!allowedRoles.includes(role ?? '')) {
  return NextResponse.json(
    { success: false, error: { code: 'FORBIDDEN', message: 'Insufficient permissions' } },
    { status: 403 }
  );
}
```

## 7. Performance Optimization

### Projection — Never Fetch Full Documents for Lists

```js
// BAD — fetches entire document including description, SEO fields, all variants
const products = await Product.find({ isActive: true });

// GOOD — fetch only what the list card needs
const products = await Product.find(
  { isActive: true },
  {
    slug: 1,
    name: 1,
    images: { $slice: 1 },   // primary image only
    'variants.price': 1,
    'variants.sku': 1,
    isActive: 1,
  }
).limit(12).lean();           // .lean() returns plain objects, 2–3× faster
```

### `.lean()` on All Read-Only Queries

`.lean()` skips hydrating Mongoose document instances and returns plain JS objects. For read-heavy public routes this is a 2–3× performance improvement with one word added to the query.

### Cursor-Based Pagination at Scale

```js
// Offset-based (fine for < 10,000 products)
const products = await Product.find(filter).skip(page * limit).limit(limit);

// Cursor-based (switch to this at scale — much faster at large offsets)
const products = await Product.find({
  _id: { $gt: new ObjectId(lastSeenId) },
  ...filter
}).limit(limit).sort({ _id: 1 });
```

### Cloudinary Image Optimization

```
// Serve correctly-sized, format-optimized images automatically

// Product card (400px wide):
https://res.cloudinary.com/{cloud}/image/upload/f_auto,q_auto,w_400/{publicId}

// Product detail page (800px wide):
https://res.cloudinary.com/{cloud}/image/upload/f_auto,q_auto,w_800/{publicId}

// f_auto: serves WebP to modern browsers, JPEG to older
// q_auto: picks quality based on content complexity
// w_N:    resize to N pixels (Cloudinary caches the transform)
```

### Avoid Over-Fetching in Admin Panel

Use query params to request only what each view needs:

```
GET /api/admin/products?fields=name,slug,isActive,variants.stock
```

Add a `fields` projection parser in your route handler that maps allowed field names to MongoDB projection objects. This prevents the admin list page from fetching product descriptions and SEO fields it will never display.

## 8. Tradeoffs

### Why MongoDB Over PostgreSQL

Products with variants, image arrays, and bilingual fields map naturally to documents. In SQL this would require `products`, `product_variants`, `product_images`, and `product_translations` — four tables with four joins on every product page load. The MongoDB document contains all of this in a single read.

**Where MongoDB loses:** Payroll and financial calculations. Joining attendance records to staff to compute monthly salaries requires application-level aggregation that PostgreSQL would do more elegantly with window functions and `GROUP BY`. This logic lives in Node.js code instead of SQL. At current scale that is fine; at 500+ employees it becomes painful.

The pragmatic call: use MongoDB for everything and accept this tradeoff. Rewriting the DB at 500 employees is a good problem to have.

### Embedding vs Referencing

| Embedded | Referenced |
|----------|------------|
| Product images | Product → Category |
| Product variants | Payroll → Staff user |
| Order → item snapshots | Attendance → Staff user |
| Staff → salary details | Inventory movement → Inventory item |
| Payroll → deductions | Order → Customer |

**Rule applied consistently:** If data is always fetched together and changes together, embed. If data has its own lifecycle or is referenced from many places, reference.

### Known Limitations

| Limitation | Impact | Fix When Needed |
|------------|--------|-----------------|
| No real-time stock sync between orders and inventory | Minor at current scale | MongoDB transactions + event queue at e-commerce launch |
| No optimistic concurrency on stock updates | Two simultaneous orders could oversell | `findOneAndUpdate` with version key when adding cart |
| Payroll generation not idempotent without unique index | Duplicate drafts if called twice | Add `{ userId, month, year }` unique index on payroll collection |
| `skip/limit` pagination degrades at large offsets | Slow at 10k+ products | Switch to cursor-based pagination |

Middleware extracts the tenant from the subdomain (`masala-x.yourplatform.com`) and injects it into every request. The schema work to add this later is significant — worth adding a `tenantId` placeholder field now even if it always holds the same value, so the index structure is ready.
