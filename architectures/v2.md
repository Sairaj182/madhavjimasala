# 1. Architecture Philosophy

This project is intentionally designed in phases.

The goal is NOT to over-engineer for a tiny business.

The goal is:

* Keep implementation simple today
* Keep migration paths clean tomorrow
* Avoid technical debt
* Maintain industry-standard folder structure
* Learn scalable SaaS engineering practices properly

Current business scale:

* Small staff team (~5 people)
* Owner-managed operations
* Minimal operational complexity
* Internal admin panel
* Product showcase website
* Future ecommerce possibility

Therefore:

* We avoid unnecessary microservices
* We avoid dedicated backend servers
* We avoid event-driven complexity
* We avoid enterprise-grade abstractions too early

But:

* We structure code so scaling later is easy

# 5. Prisma + MongoDB Strategy

## Why Prisma instead of Mongoose

Reasons:

* Better TypeScript support
* Better schema management
* Better DX (developer experience)
* Centralized schema definition
* Cleaner generated types
* Easier future migration
* Industry-standard modern stack

---

## Prisma Package Structure

Location:

```txt
packages/db/
```

Structure:

```txt
packages/db/
│
├── prisma/
│   └── schema.prisma
│
├── src/
│   ├── client.ts
│   └── index.ts
│
├── package.json
└── tsconfig.json
```

---

## Prisma Client Singleton

We use singleton Prisma client architecture.

Reason:

Next.js hot reload can create too many DB connections during development.

Singleton prevents connection explosion.

Example:

```ts
import { PrismaClient } from "@prisma/client";

const globalForPrisma = globalThis as unknown as {
  prisma: PrismaClient | undefined;
};

export const prisma =
  globalForPrisma.prisma ??
  new PrismaClient();

if (process.env.NODE_ENV !== "production") {
  globalForPrisma.prisma = prisma;
}
```

---

## MongoDB ObjectId Strategy

MongoDB uses ObjectIds.

Prisma schema example:

```prisma
id String @id @default(auto()) @map("_id") @db.ObjectId
```

Referenced IDs:

```prisma
categoryId String @db.ObjectId
```

Prisma relations in MongoDB are NOT real joins.

They are application-level references.

# 9. Attendance + Payroll Architecture

Current business size:

Very small.

Therefore:

Attendance system remains intentionally simple.

---

## Attendance Strategy

One attendance document per staff per day.

Fields:

* userId
* date
* status
* checkIn
* checkOut
* notes

---

## Payroll Strategy

Payroll is generated monthly.

Process:

1. Read attendance
2. Calculate payable days
3. Generate payroll snapshot
4. Store payroll document

Payroll becomes immutable after approval.

---

## Important Design Decision

Payroll stores salary snapshots.

Reason:

If salary changes later,
old payroll records must remain historically correct.
